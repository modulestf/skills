# Check C: Module Structure

> **Part of:** [terraform-module-reviewer](../SKILL.md)
> **Purpose:** The operative fails-when and severity rules of Check C. Rule numbers refer to the [Mandatory Rules](../SKILL.md#mandatory-rules) in SKILL.md.

**Reads:** the changed `.tf` files, the module file layout, and the `variables.tf` of every local submodule a `module` block in the scope of [Pass-through to a Local Submodule](#pass-through-to-a-local-submodule) calls, judged against [Module Structure Patterns](../../terraform-module-maintainer/references/module-structure.md), [Service Archetypes](../../terraform-module-maintainer/references/service-archetypes.md), and tiers 1, 2, and 5 of the [Coverage Checklist](../../terraform-module-maintainer/references/coverage-checklist.md).

**Provider facts:** four rules here can need a provider page, read per [Rule 2](../SKILL.md#rule-2-provider-schema-from-mcp-never-from-memory) as [Check B](check-b-coverage.md) reads it. `structure.schema-shape-flattened` needs the block and argument names of the provider's structure. `structure.sibling-block-asymmetry` needs them when it compares a dynamic block against the schema rather than its siblings. `structure.sibling-argument-omitted` needs to know whether the resource's own schema carries the routing argument. `structure.docs-contradict-code` needs a page when whether the promised behaviour happens depends on what a resource or data source does with its arguments, for example which of a policy document data source's inputs end up in which of its attributes. When that page is unavailable, the rule does not fire on that case, and its `rule_id` is named in the `review.check-not-run` of [Rule 4](../SKILL.md#rule-4-a-check-that-cannot-run-is-a-finding) with the type and version. A case these rules decide from the module's own code alone still fires.

**Fails when:**
- A resource added by the change ignores conditional creation, so `create = false` no longer produces an empty plan.
- An output added by the change has no `try()` fallback, or uses a fallback that changes the output type.
- A new variable has no explicit `type`, uses `any` without a stated reason, or has no `description`; a new output has no `description`.
- A nested object input flattens or renames the provider's structure instead of matching it.
- A dynamic block added by the change covers fewer fields than its sibling blocks, or than the schema for that block.
- Code lands in the wrong file for the module's archetype, for example identity resources inline in `main.tf` where the archetype calls for a separate file (`structure.wrong-file`). The archetype's extra files are optional in the profile, whose [Module layout](../../terraform-module-maintainer/profiles/terraform-aws-modules/PROFILE.md#module-layout) says the absence of one is not a defect. So this fires only when the directory at the head already has the file the archetype names for that group, such as `iam.tf`, and the change adds blocks of that group to another file. A directory with no such file, new or existing, gets no finding for keeping the group in `main.tf`.
- Tags or labels are not propagated to a resource added by the change that supports them.
- A new `enable_*` boolean defaults to `true`, a new `create_*` boolean defaults to `false`, or a new `attach_*` boolean defaults to `true`, against [Feature Flag Naming and Default Polarity](../../terraform-module-maintainer/references/module-structure.md#feature-flag-naming-and-default-polarity).
- A resource block the diff adds or modifies puts `count` or `for_each` after another argument, or puts `tags` or `labels` anywhere but last, against [Argument Order in a Resource Block](../../terraform-module-maintainer/references/module-structure.md#argument-order-in-a-resource-block). Only blocks the diff touches are in scope: ordering in untouched blocks of the same file is not this change's defect.
- The change adds a `provider` block carrying an `alias`, adds a `provider = <provider>.<alias>` argument to a `resource` or `data` block, or adds a `providers = {}` argument to a `module` block, anywhere in the module under review. `examples/` is a root configuration, not the module: an example that demonstrates a cross-region or cross-account pattern declares aliases legitimately and is out of scope for this rule. Against [One Provider Configuration per Module](../../terraform-module-maintainer/references/service-archetypes.md#one-provider-configuration-per-module). The caller composes regions and accounts; a module that carries its own aliases decides for every consumer which ones exist.
- A `validation` or `precondition` block added by the change has an `error_message` that names neither the accepted values or the bound nor the value that was received, against [Error Messages Name the Offending Value](../../terraform-module-maintainer/references/module-structure.md#error-messages-name-the-offending-value).
- An input the change adds or forwards is read only inside a branch another input switches off, so setting it does nothing and raises no error. The module's own creation flag `create` is not the switching input: every resource sits behind it and that is the intended shape. A feature flag named `create_<x>`, `attach_<x>`, `enable_<x>`, `manage_<x>` or `<x>_enabled` is not the switching input for an input whose name contains `<x>` as a run of whole `_`-separated tokens: `enable_log` exempts `log_group_name` and not `catalog_id`. For example `create_iam_role` for `iam_role_policies`, `create_policy` for `source_policy_documents`, `attach_policy` for `policy`, `enable_flow_log` for `flow_log_destination_arn`, `performance_insights_enabled` for `performance_insights_retention_period`, or `manage_default_security_group` for `default_security_group_ingress`: that input configures the thing the flag turns on. These are the family's feature flags, named in [Feature Flag Naming and Default Polarity](../../terraform-module-maintainer/references/module-structure.md#feature-flag-naming-and-default-polarity), plus two forms the family also uses: `<x>_enabled`, as `terraform-aws-rds` does for Performance Insights, and `manage_<x>`, as `terraform-aws-vpc` does for its default security group. Such a flag that switches off an input whose name does not contain `<x>` is the switching input. The rule is one input silently disabling another. An attribute a submodule's type discards on conversion is `structure.passthrough-field-drift`, and this rule is silent on it.
- A `module` block calling a local submodule forwards a root input whose attribute set or unset value differs from the submodule variable it lands in. The procedure is in [Pass-through to a Local Submodule](#pass-through-to-a-local-submodule).
- A resource block the change adds omits a routing argument - `region`, `project`, `subscription_id` - that the resource's own schema carries, whose input exists, and which at least 80 percent of the other comparable resource blocks in that file set from a module input. `data` blocks do not count, a resource whose schema has no such argument is neither counted nor reported, and under 5 comparable blocks the rule stays silent. Run the count on the head under review; never recall it.
- A comment added by the change that directs a scanner to ignore, skip, or suppress a finding states no reason for accepting the risk, neither on the directive line nor on a comment line next to it, against [Scanner Suppressions](../../terraform-module-maintainer/references/module-structure.md#scanner-suppressions).
- Documentation the change adds or touches - a README section, a variable `description`, an example comment - describes behaviour no code path implements: an input it says is read, a value it says is reused, a mode it says is supported.
- An input whose accepted values are a closed set - a mode, an enum, a type name - has no `validation` block, or has one that is commented out, so a typo is accepted at the input and surfaces far from it, as a count of zero or an index error downstream.
- The change uses a core language function or block introduced after the declared `required_version`, calls a `provider::<name>::<fn>` function under a floor below 1.8, or uses a function or block only OpenTofu has in a module whose constraint admits Terraform, against [Version floors](../../terraform-module-maintainer/profiles/terraform-aws-modules/code-conventions.md#version-floors).
- A `versions.tf` the change touches declares a lower floor than the thing it calls - the root against a submodule under `modules/` it calls, or an example against the module it calls - against [Version floors](../../terraform-module-maintainer/profiles/terraform-aws-modules/code-conventions.md#version-floors). Scope is those files and their counterparts; a caller declaring more than its callee is silent.
- A comment the change adds restates what the code plainly says to a senior DevOps or SRE reader, against [Comments](../../terraform-module-maintainer/profiles/terraform-aws-modules/code-conventions.md#evidence-comments-copied-values-and-availability).
- A comment the change adds asserts a service limitation, a provider defect, an ordering requirement or other non-obvious behaviour with no link to an official source and no date, against [Evidence](../../terraform-module-maintainer/profiles/terraform-aws-modules/code-conventions.md#evidence-comments-copied-values-and-availability). Pre-existing comments, the `####` section-header banners and a scanner suppression are out of scope, and a suppression keeps `structure.suppression-unexplained`.
- A constant the change adds was copied out of a document - an IAM policy or SCP, an AWS account number, a literal ARN, a service principal, a condition key, a hosted zone ID - and carries no comment naming the source URL and the date, against [Copied values](../../terraform-module-maintainer/profiles/terraform-aws-modules/code-conventions.md#evidence-comments-copied-values-and-availability). A value the module computes, one from a `data` source, and a policy built from the module's own inputs are derived rather than copied. A value inside a comment, illustrating a format or a conversion, is not a constant the module uses and never fires this.
- A `validation` block the change adds depends on another variable or on how the module will be used, encodes a compliance or policy judgement, or re-implements a service-side naming or format rule, each as scoped by [Validation](../../terraform-module-maintainer/profiles/terraform-aws-modules/code-conventions.md#validation). `structure.validation-missing` is unaffected: a closed value set still needs its block.
- An ARN the change adds writes `arn:aws:` as a literal, or hard-codes an account ID or a region, where the module builds the ARN and `local.partition` is available or addable, against [ARNs and partitions](../../terraform-module-maintainer/profiles/terraform-aws-modules/code-conventions.md#arns-and-partitions). A comment naming the partitions the literal is right for, carrying its source and date, is silent, and so is an ARN appearing inside a comment as an example of a format.

**Severity:**
- CRITICAL when a secure default is weakened: encryption, public access, logging, or deletion protection.
- HIGH when conditional creation is broken, an output will error instead of returning null, or a nested input does not match the schema shape. HIGH too when documentation promises behaviour no code path implements (`structure.docs-contradict-code`); an input the code reads nowhere is the other rule, `structure.input-ignored-in-branch`.
- HIGH when a new resource block omits a routing argument its siblings set (`structure.sibling-argument-omitted`), or an input ignored in a branch changes which resources are created, or grants or restricts access (`structure.input-ignored-in-branch`); CRITICAL when setting it destroys resources an existing caller already has, MEDIUM only when the effect is cosmetic.
- HIGH when the change uses a core language feature the declared `required_version` does not reach (`structure.feature-above-version-floor`); the `summary` quotes the documentation page that gives the introducing version and the date it was read. This is the core language axis and `coverage.argument-above-min-version` in Check B is the provider-schema one, so they stay separate.
- HIGH when a caller declares a lower floor than the thing it calls (`structure.version-floor-understated`), and CRITICAL when the two constraint sets do not intersect at all - an upper bound excluding the callee's floor - because no version satisfies both and the configuration cannot initialize.
- HIGH when an ARN the change adds hard-codes the partition, an account ID or a region the module could derive (`structure.arn-partition-hardcoded`).
- MEDIUM when a forwarded input's unset value differs between the root and the submodule (`structure.passthrough-default-drift`): a root caller who sets nothing gets a value the submodule does not declare, and nothing errors. HIGH when the root yields null into a submodule variable that has a non-null default and no `nullable = false`, so the submodule receives a value its own default excludes, or when the root's own documentation states the submodule's value. LOW when the input feeds only tags, a description or a name. Where the root's value weakens a secure default the submodule keeps, that is `structure.insecure-default` at CRITICAL, reported once.
- MEDIUM when the submodule has an attribute the root cannot pass (`structure.passthrough-field-drift`): the submodule's capability is unreachable through the root, the band of an optional argument left unexposed. HIGH when that attribute is required in the submodule type, so every non-null value fails conversion at plan. For an attribute the root has and the submodule discards, the finding is `structure.passthrough-field-drift`, never `structure.input-ignored-in-branch`, at that rule's band: HIGH when it changes which resources are created or grants or restricts access, MEDIUM otherwise.
- MEDIUM when a must-pass structural convention is missed: missing `type`, missing `description`, wrong file, missing tag propagation, a scanner suppression with no reason for accepting the risk, a closed value set whose `validation` block is absent or commented out (`structure.validation-missing`; the wording of a message a present block does emit is `structure.validation-message-uninformative`).
- MEDIUM when a feature flag's prefix and its default disagree, or the module declares its own aliased provider configuration. Where a second provider configuration also changes what the caller has to pass in, Check A owns that part too.
- MEDIUM when a comment the change adds restates the code (`structure.comment-redundant`), or asserts a limitation, a defect or an ordering requirement with no source and no date (`structure.comment-unsourced`).
- MEDIUM when a copied constant carries no source URL and date (`structure.copied-content-unattributed`), or a `validation` block reaches past its own variable (`structure.validation-overreaching`).
- LOW when a should-pass convention is missed: grouping, section headers, argument order inside a touched resource block, naming consistency, an error message that tells the consumer neither the bound nor the value received.

`rule_id` prefix: `structure.`, for example `structure.create-flag-ignored`, `structure.output-no-try`, `structure.variable-untyped`, `structure.missing-description`, `structure.schema-shape-flattened`, `structure.sibling-block-asymmetry`, `structure.insecure-default`, `structure.wrong-file`, `structure.grouping`, `structure.flag-polarity`, `structure.argument-order`, `structure.multi-provider`, `structure.validation-message-uninformative`, `structure.suppression-unexplained`, `structure.input-ignored-in-branch`, `structure.sibling-argument-omitted`, `structure.docs-contradict-code`, `structure.validation-missing`, `structure.feature-above-version-floor`, `structure.version-floor-understated`, `structure.comment-redundant`, `structure.comment-unsourced`, `structure.copied-content-unattributed`, `structure.validation-overreaching`, `structure.arn-partition-hardcoded`, `structure.passthrough-field-drift`, `structure.passthrough-default-drift`.

## Pass-through to a Local Submodule

A root module that forwards its inputs to a submodule declares every field and default twice, once in its own type and once in the submodule's variables. The two copies drift with no error. This procedure compares them, and reads everything off the expression and type text so two runs list the same fields.

**Scope.** Every `module` block in the module root or in a submodule, with a `source` beginning `./` or `../`, that the diff adds or whose arguments it changes. Also every such block, touched or not, when the diff changes the called submodule's `variables.tf`, or changes the type or default of a root variable one of the block's arguments forwards. Calls under `examples/` are a root configuration (Check D), and calls under `wrappers/` are generated (Check E); both are out of scope.

**Forwarded.** An argument of that block is forwarded when its expression is one reference to a root input, or several joined only by `coalesce()`, `try()` or `<ref> != null ? <ref> : <other ref>`. A reference is `var.<name>`, an attribute path under it, or an attribute path under `each.value` where the `for_each` map's values are the elements of a root variable, unchanged, whether written in the `for_each` or in a local it reads: `{ for k, v in var.x : k => v if <condition> }` qualifies, `k => merge(v, {...})` does not. Any other expression - a literal, `each.key`, a resource attribute, `merge()` or any other function - is the author choosing a value, not forwarding one, and is not compared.

**Unset values.** The root side is what the expression yields when the caller sets none of the inputs it reads: `value` for an `optional(type, value)` attribute, null for an `optional(type)` attribute, the `default` for a variable. A required variable or attribute has no unset value and skips step 2. The submodule side is the variable's `default`. Terraform substitutes that default for a null argument when the variable has `nullable = false`, and substitutes an `optional(type, value)` default for a null attribute, so in those two cases a null on the root side is no difference.

1. **Attribute set** (`structure.passthrough-field-drift`). Walk the root-side type and the submodule variable's type together, at every depth under the forwarded argument; with several references, walk each one's type. An attribute the submodule type has and the root type lacks is a finding: no root caller can set it. An attribute the root type has and the submodule type lacks is a finding: conversion discards it, so what the caller sets there does nothing. When the call forwards any attribute of `each.value` or of one root object, a submodule variable the call does not set by any expression is the first case too.
2. **Unset value** (`structure.passthrough-default-drift`). For each forwarded argument, and each attribute both types carry, compare the two unset values after the substitution above. `null`, `[]` and `{}` are three different values.

The finding's `file` and `line` are where the root-side type declares the attribute, or the object type that lacks it, because that is where the fix goes. The `summary` names the submodule variable and its line.
